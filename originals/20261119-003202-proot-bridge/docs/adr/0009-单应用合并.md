# ADR-0009：单应用合并，原版功能作主、当前安全层作补

- 状态：提议（等你确认“之前那样子”的具体所指）
- 日期：2026-11-19
- 相关：ADR-0005、ADR-0008、`docs/原版桥接.md`

## 背景

现在仓库里有两个桥接器：

1. `units/bridge/bridge.mjs`（1618 行）：当前主桥，策略/队列/补发/图片/群消息层做得好，但会话只按 chatKey 存一个 id，`/ws`、`/ls`、`/model`、面板写配置都标着“未实现”。
2. `units/legacy/app/`：从原版 `napcat-dsh-bridge` 复原的应用，有 `SessionRegistry`、多工作区、`/ws`、`/model`、`/export`、DSH API/headless 双传输、面板写接口，但以 opt-in 单元存在，和主桥二选一。

这不是“整合”，是把两份逻辑并排放。用户要的是：**分析两份代码，取原版的会话/工作区/面板精华，去掉它的单体与不安全部分；保留当前主桥的策略/补发/消息层；模块回到原版“一个 app”的形态。**

## 代码对照（证据）

| 能力 | 原版 `legacy` | 当前 `bridge` | 结论 |
| --- | --- | --- | --- |
| 每聊天多工作区 | `SessionRegistry` / `/ws` / `/ls` | 固定 `cfg.workspace` | 取原版 |
| 会话目录/归属/恢复 | `session-manager.js`、`session-meta.js` | 单个 `sessions.json` 映射 | 取原版 |
| 模型切换 | `/model` + `--patch` | 标“未实现” | 取原版 |
| 会话导出 | `export.js` + `/export` | 透传 DSH | 取原版 |
| 面板写配置/重启 | `admin.js` + `panel.js` 写接口 | 只读 | 取原版接口，保留当前渲染 |
| DSH 传输 | API + headless 双通道 | 只有 headless | 取原版双通道 |
| 访问策略 | 有，但规则较旧 | 角色/白名单/群 @ 更硬 | 取当前 |
| 补发/去重/告警 | 有 outbox，但较旧 | 重试/补发/seen/告警更完整 | 取当前 |
| 消息层 | 引用/图片/表情的基础 | 引用、表情、暂不支持、群 @、AI 披露、成员会话 | 取当前 |
| 输出档位/自动压缩 | 无 | 四档 + 摘要压缩 | 取当前 |
| 群上下文 | 无 | BM25/水位/图片保底 | 取当前 |
| 拟人化/交互 | `persona` + `interactions` | `humanize` + `interactions` | 以当前实现为准，接口兼容原版 |
| 图片安全 | 有 SSRF 检查 | DNS/IP/重定向/大小限制更完整 | 取当前 |
| 面板 UI | 原版 client/css 有缺行 | 当前只读渲染完整 | 先用当前渲染，原版写接口后接 |
| 启动安全 | `TYPE=exec`，不 chroot | 零开机动作/私有 namespace | 保留当前 |

原始字节的补充证据：

- `tinda-bot-v0.1.3.zip` / `v0.2.2.zip` 的 `app/src/bridge.js` 是 **2358 行**，sha256 `9025722b…`，与 `recovered/root/.../bridge.js` 完全一致；这不是聊天记录里“看见”的，是旧模块产物里留存的原始文件。
- 该文件在 `summarize()` 前有一段截断（`node --check` 报 `Unexpected identifier 'invokeDsh'`），说明旧 zip 是编辑中途打出来的；当前 2191 行版本修好了这段。**不能盲目按字节还原，必须按时间线修补。**
- `/tmp/dsh-sessions` 的 34 份完整转录里有 95 次 `edit`、3 次 `write`、40 次 `read`；可按 `tool/call` → `tool/result` 的顺序重放，得到每个文件的版本链。之前只看助手正文，才会得出“面板/命令不可恢复”的结论。

## 可选方案

### A. 单应用：原版 app 作主，当前安全层并入（推荐）

- 模块根目录恢复 `app/`：`app/src/index.js`、`app/src/bridge.js`、`app/src/session-*`、`app/src/panel*`，一个进程、一份配置、一份状态。
- 以修好的原版 `bridge.js`（2191 行）为骨架，把当前 `message/policy/group-context/output/typing/alerts/image` 作为独立模块接进去，不复制逻辑。
- `units/legacy` 删除（源码进 `originals/` 只读存档），`units/bridge` 删除，`bin/run-bridge.sh` 直接起 `app/src/index.js`。
- 保留 `units/napcat`、`units/web`、`units/dsh` 作为外围服务；桥接只有一份。
- 开机仍零动作，手动 `unit.sh start bridge`；v0.2.37 的 namespace/chroot 安全层不动。

### B. 当前 bridge 作主，原版功能逐项搬进来

- 保留 `units/bridge`，把 `SessionRegistry`/`/ws`/`/model`/`export` 搬进当前 `bridge.mjs`。
- 风险：当前 `sessions` 是单 id 映射，换多工作区要重写回合/压缩/补发三处；等于把原版最复杂的部分拆碎重拼。
- 好处：当前测试全保留。

### C. 保持两个桥接，只做默认切换

- 把 `legacy` 设为默认，当前 `bridge` 留作回退。
- 不解决双状态、双面板、双配置；用户已经明确反对“逻辑拼接”。不采用。

### D. 什么都不做

- 继续维护两个桥接，缺陷是同一份消息可能两套行为、两份配置、两个面板；不采用。

## 决定

采用 **A**，但分两步，避免一次性拆掉可运行版本：

1. **结构合并**：新建 `app/`，以修好的原版 `bridge.js` 为骨架；把当前安全模块按“纯函数/独立类”接进去；`legacy` 和当前 `units/bridge` 只保留一个入口。
2. **功能收口**：优先接 `/ws`、`/ls`、`/model`、`/export`、面板写配置；每接一项，从当前测试/原版测试各拿一条用例。

在这两步完成前，不再发新的“并行单元”版本；现有 v0.2.43 只作为回退。

## 代价与残余风险

- 原版 `panel-client.js`/`panel.css` 仍有缺行，第一步先用当前只读渲染；写配置接口先做，UI 后补。
- 原版 `commands.js` 只有 477 行复原，`/model` 的后半段需要按原版 `bridge.js` 的调用点补。
- 双传输（API/headless）会带来更多失败路径；先用配置开关保留，默认 headless，API 只作为可选。
- 合并期间测试要重写到 `app/test/`；旧 `units/bridge/test-*` 不能直接复用路径。
- 这是一次行为级重构，必须单独发版（v0.3.0），不能混在补丁里。

## 何时重审

- 如果原版 `SessionRegistry` 与当前补发队列在“回合中切工作区”上无法共存，回退到 B，并把多工作区标为实验特性。
- 如果面板写配置无法在不暴露 token/任意路径的前提下接回，面板保持只读，写配置只走 `/data/adb/tinda-bot/etc/` 文件。
