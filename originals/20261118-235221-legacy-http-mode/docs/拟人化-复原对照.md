> 结论不能靠印象，得对着旧源码一条条比。旧 `persona.js` 已随项目一起丢失，

## 1. 三项功能的有无

| 功能 | 旧版位置 | 现在 | 结论 |
| --- | --- | --- | --- |

## 2. 参数对照

旧版默认值（恢复片段里 `createPersona` 的 `target`）：

| 项 | 旧版 | 现实现 | 差异 |
| --- | --- | --- | --- |
| 打字速度 | `cpm` 220（≈272ms/字） | `perCharMs` 25 | 现实现快约 11 倍 |
| 单条前延迟 | 夹在 700–5200ms | 夹在 350–1800ms | 现实现更短 |
| 抖动 | ±35% | ±25% | 现实现更稳 |
| 第一条前导延迟 | `firstDelayMs` 1500 | 无（第一条不等待） | 现实现不模拟「看到消息」的停顿 |
| 最多几条 | `maxBursts` 6 | `maxBubbles` 3 | 现实现更保守 |
| 列表拆分门槛 | 显示宽度 320 | 无（不按列表项拆） | 现实现少一个能力 |
| 单条硬上限 | `min(hardLimit, maxReplyChars)`，默认 4000 | `cap` 4000 | 一致 |
| 条间停顿 | 450–1800ms | 由 perChar 折算，总计封顶 4000ms | 现实现多了总时长上限 |
| 字素切分 | `Intl.Segmenter`（防 ZWJ emoji 被切坏） | 未用 | 现实现按 code point 切 |

旧版还有个细节：`hardLimit` 取 `min(配置, maxReplyChars)`，注释写明
「否则 persona 切到 4500、bridge.push 又按 4000 二次切，代码围栏会被撕开」。
现实现只有一处 `cap`，等价地避免了二次切。

## 3. 输入状态的旧语义（恢复片段里有）

```js
inputStatus: {
  enabled: c.inputStatus?.enabled !== false,
  onReceive: c.inputStatus?.onReceive === true,   // 收到消息立刻亮一下
  keepaliveMs: clampNum(c.inputStatus?.keepaliveMs, 0, 120000, 8000),
  ackOnSlowMs: clampNum(c.inputStatus?.ackOnSlowMs, 0, 600000, 0),
  eventStart: clampNum(c.inputStatus?.eventStart, 0, 16, 0),
  eventStop: clampNum(c.inputStatus?.eventStop, 0, 16, 1)
}
```

调用点（`bridge.js`，恢复到了）：只对 `inbound.kind === 'private'` 创建，
`start()` 在进轮次前、`stop()` 在 `finally`。

现实现 `typing.mjs` 对齐了 **enabled / keepaliveMs / eventStart / eventStop** 四项，
没实现 `onReceive`（现实现是「一进轮次就亮」，已经覆盖）和 `ackOnSlowMs`（慢回执，
属于另一件事，要做得单独加，不能塞进输入状态里）。
