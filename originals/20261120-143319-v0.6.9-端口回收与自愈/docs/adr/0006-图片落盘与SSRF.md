# 0006 图片落盘与 SSRF 防线

## 背景

旧 `bridge.js` 的 `collectImages()` 会把 QQ 图片下载到当前 workspace 的 `inbox`，
再把本机路径交给模型；重建后只写 `[图片]` 占位，模型看不到图（`docs/待恢复清单.md` #13）。
v0.2.35 恢复下载，但图片 URL 来自 QQ 用户，属于不可信输入：直接 `fetch` 会引入
SSRF（访问 127.0.0.1/内网/云元数据）和任意本地文件读取面，必须先把边界定死。

## 可选方案

1. **什么都不做**：继续只写 `[图片]`。最安全，但用户发图等于没发，旧行为没恢复。
2. **把 URL 直接交给模型/让模型自己下载**：桥接器简单，但模型工具未必能访问，
   且把一个可访问内网的 SSRF 面交给模型，不可控。
3. **桥接器下载到 state，再把本机路径交给模型（选中）**：下载面留在桥接器，
   可以做协议/地址/类型/大小/超时校验；模型只读本机文件。
4. **只接受 NapCat 的本地缓存路径**：最安全，但当前 NapCat 没给稳定路径，
   需要改 NapCat/插件，超出本仓库边界。

## 决定

选 3，具体边界：

- 只允许 `http:`/`https:`；拒绝 `file://` 和绝对路径；
- 默认拒绝 localhost、私网、链路本地、多播，含 IPv4-mapped IPv6；
- 域名先 DNS 解析，再逐地址检查；
- 手动跟随 3xx，每一跳重新校验，防止公网 URL 302 到 127.0.0.1；
- content-type 白名单 png/jpeg/gif/webp；Content-Length 与流式读取双重大小上限；
- 默认 10MB / 8 张 / 8 秒；目录 0700、文件 0600；
- 全部失败时在正文前明确告诉用户「图片没能读取」，不让模型假装看过。

## 代价与残余风险

- 下载是串行的，8 张各 8 秒时最坏会拖慢一轮；后续可改并发/更短超时。
- DNS 校验与真正 `fetch` 之间存在 TOCTOU：校验时解析到公网、请求时重新解析到内网
  仍可能发生；当前没有绑定 IP 的 dispatcher。
- 图片落盘不自动清理；模型能读，root 也能读。
- `BRIDGE_IMAGE_ALLOW_PRIVATE_HOSTS=1` 会削弱这条防线，只给内网 NapCat 用。
- 没有真 QQ/CDN 环境，URL 行为以假图片服务器为准。

## 何时重审

- 增加视频/文件/图片上传，或换图片源；
- NapCat 提供稳定的本地缓存路径（可改成方案 4）；
- 出现 SSRF、目录穿越或权限事故；
- 需要支持并发下载/自动清理时。
