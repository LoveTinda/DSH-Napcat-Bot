# 0016 token 以文件为准，并给网关一个自我说明页

## 背景

「打不开 / 卡在验证中」反复出现，而每次排查都缺同一样东西：**服务器自己说了算的事实**。
具体证据（真机，2026-11-20）：

```text
GET /?k=<action.sh 打印的 token>        → 200，但没有 Set-Cookie
GET /_/status?k=<同一 token>            → 401
```

首页能打开说明进程和证书都没问题，token 不被接受说明**网关认的 token 与用户手上那份不同**。
两种成因都在代码里：

1. token 只在启动时从环境变量读一次。之后 `secrets/web.token` 被重新生成（换 token、
   另一处初始化、升级后重跑 `run-web.sh`），运行中的进程仍是旧值。
2. proot 内外的 `$DATA` 可能不是同一个目录（模块目录在 guest 里被 bind 到别的路径）。
   于是网关读 guest 那份、`action.sh` 读宿主那份，各自都对，就是不一样。

另外两个把「慢」放大成「坏了」的缺陷：

- `new URL(req.url)` / `res.writeHead()` 抛错被 `uncaughtException` 接住，进程不死，
  但**那个请求永远没有响应**，浏览器端就是无限转圈。
- 没设 keep-alive 超时，node 默认 5 秒关空闲连接；浏览器正好复用时收到 RST，
  表现为偶发 `ERR_CONNECTION_RESET`。

## 可选方案

1. **什么都不做**：继续靠手工探测 + 让用户重试。
   代价：每次都要猜，且「我这边 200 / 你那边不行」这种对账永远没有第二份证据。
2. **换成用户名密码 / 关掉鉴权**：改动大、安全性下降，且没解决「哪份凭据生效」的问题。
3. **token 以文件为准 + 公开自我说明 + 全链路不再悬空**（采纳）。

## 决定

1. **token 的唯一真源是文件**。候选顺序：`WEB_TOKEN_FILE` → `$TINDA_DATA/secrets/web.token`
   → `/data/adb/tinda-bot/secrets/web.token`，取第一个有内容的。每次鉴权瞄一眼文件，
   变了就跟上，**不必重启**。环境变量只作启动时的兜底，不再是一言堂。
2. **`GET /__info` 公开**（不含 token 本身）：版本、pid、脚本路径、cwd、数据目录、
   token 指纹（SHA-256 前 8 位）、每个候选文件的 mtime/长度/指纹、监听参数。
   指纹不可逆，不构成凭据泄露；它让「是不是同一份 token」变成可核对的事实。
3. **登录框显示指纹**：输错的 token 会当场算出指纹并与服务器比对，直接显示两边各是什么。
   `action.sh` 也打印同一指纹，便于与 `/__info` 对照。
4. **请求不再悬空**：入口整体 try/catch，异常一律回 500 并记日志；反代里 `writeHead`
   失败、下游中途断流都有明确收尾。
5. **keep-alive 65 秒**（比浏览器常见 60 秒长一档），headersTimeout 70 秒。
6. **访问日志**：`[web] GET / 200 3ms from=… ua=…`，跳过轮询与静态资源，4xx/5xx 全记。

## 代价与残余风险

- 每请求多 1~3 次 `stat`（候选文件），可忽略；换来的是「文件一改就生效」。
- `/__info` 把路径、pid、token 指纹暴露给同网段。这些信息对攻击者价值有限（token 本身
  和证书私钥都不在里面），但确实扩大了信息面；已只监听必须带 token 的端口，且不提供写操作。
- 指纹是 8 位十六进制，理论上可被枚举碰撞，但需要先能对 128 位随机 token 做在线爆破，
  实际不可行。
- **没有**解决「proot 里 $DATA 与宿主不一致」这个更深的坑，只是让它变得可见（/__info 的
  tokenFiles + 启动横幅）。彻底统一数据目录要另开一份 ADR，且会影响已装机器的状态迁移。

## 何时该重审

- 出现需要把 `/__info` 也纳入鉴权的场景（例如暴露到公网）；
- 真机日志证明 `$DATA` 分裂仍在发生，且用户持续被它绊住 —— 那就该做数据目录统一迁移；
- token 改为可轮换（多设备 / 多人）时，候选文件与指纹机制需要重新设计。
