# 0014 Android 的幽灵进程清理与 cgroup 冻结

## 背景

模块的 web/bridge 是常驻进程。真机上出现过一种很难查的现象：

- 端口**能连上**（TCP 三次握手成功）
- 但**一个字节都不回**，浏览器停在「验证中…」
- 单元日志**停在半句话**，没有退出码、没有重试
- 进程**还活着**（`kill -0` 成功），心跳却停了

先前一直当成 proot 卡死。查 Termux 的已知问题（termux/termux-app#5078）后才明确：这是
**Android 12+ 的幽灵进程清理（Phantom Process Killer）与缓存应用冻结**，按**进程 cgroup**
下手——"Trimming phantom processes" 之后 `libprocessgroup: Successfully killed process
cgroup uid 10147 pid 5683`，被杀的是**整个 cgroup**，不是单个进程。

对我们的意义：从管理器（一个应用）里点「操作」启动的守护进程，是那个应用的幽灵子进程。
管理器退到后台，它就可能被**冻结（SIGSTOP）或整组 SIGKILL**。冻结的表现和「proot 卡住」
一模一样，所以之前几次判断都被带偏。

## 决定

1. 常驻进程启动时立刻自保：`oom_score_adj = -1000`（失败退 -900），并把 pid 写入
   `/sys/fs/cgroup/cgroup.procs`（能写就写），尽量脱离应用 cgroup。见 `bin/lib.sh` 的
   `protect_pid()`。
2. 子进程不继承 cgroup 变更，所以 supervisor 和每次 spawn 的子进程各保护一次
   （`oom_score_adj` 会继承）。
3. 推荐路径是**开机由 `service.sh`（magiskd 的子进程）拉起**，不是从管理器按钮起；
   `action.sh` 仍然可用，但会先在输出里说明这一点。
4. 心跳看门狗（v0.5.3）负责把「冻结→恢复」变成可见事件：心跳停了就重启整棵树。

## 代价与残余风险

- `oom_score_adj=-1000` 让内核不轻易杀它：占内存写错时代价是该单元被 OOM 保护，
  需要人自己 `unit.sh stop`。
- cgroup 迁移在部分 ROM/SELinux 策略下会失败：失败只记一行 warn，不阻塞启动。
- 冻结无法完全避免（内核级 SIGSTOP 我们拦不到），所以仍靠心跳看门狗兜底。

## 何时重审

- Android 改变幽灵进程策略（例如按 uid 而非 cgroup 处理）时；
- 模块改为由 init 的 `.rc` 服务托管时（那样根本不经过应用 cgroup）。
