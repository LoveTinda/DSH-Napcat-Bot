# 生命周期：谁管谁，谁死了会怎样

> 目的：把「独立」落成一张能对照的表。故障时直接查表，不猜。
> 最后核对：2026-11-15，四个单元都通过 `bin/unit.sh status` 实测过。

## 四个单元

| 单元 | 进程 | 入口 | PID 文件 | 日志 | 依赖 |
| --- | --- | --- | --- | --- | --- |
| `napcat` | Xvfb + QQ（内嵌 NapCat） | `bin/napcat-start-host.sh` | `run/napcat.pid` | `logs/napcat.log` | 只依赖 `/opt/QQ`、`/opt/napcat` 与本机网络 |
| `bridge` | node（proot） | `bin/run-app-proot.sh` | `run/bridge.pid` | `logs/bridge.log` | NapCat 的 3001（回发）、DSH 的 `dsh headless`；面板 6702 / admin 6701 |
| `web` | node（proot） | `bin/run-web.sh` | `run/web.pid` | `logs/web.log` | 3080 / 6702 / 6099 三个下游 |
| `dsh` | DSH 自己托管（外部） | 不拉起 | 无 | `logs/dsh.log` | 无 |

单元之间**只走端口**：`3001`（桥接器 → NapCat）、`6700`（NapCat → 桥接器，仅 HTTP 模式）、
`6099`/`6702`/`3080`（网关 → 下游）。不共享进程、不共享 PID 文件、不互相 import。

## 故障隔离矩阵

| 发生 | napcat | bridge | web | QQ 在线？ | 恢复 |
| --- | --- | --- | --- | --- | --- |
| `bridge` 崩溃 | 不受影响 | 退避重启 | 不受影响（`/bridge/` 502） | 在线 | 自动 |
| `bridge` 手动重启 | 不受影响 | 重启 | 面板短暂 502 | 在线 | 自动 |
| `web` 崩溃 | 不受影响 | 不受影响 | 退避重启 | 在线 | 自动（控制台短暂断开） |
| `napcat` 崩溃 | 退避重启 | 消息进不来（进程仍在） | NapCat 标签 502 | 短暂离线 | 自动，`-q` 快速登录续上 |
| `napcat` 手动停止 | 停止 | 进程仍在，只是没消息 | 同上 | **离线** | `unit.sh start napcat` |
| DSH 升级/重装 | 不受影响 | 每轮 spawn，自动用新的 | DSH 标签 401 | 在线 | 自动 |
| 设备/环境重启 | 需重起 | 需重起 | 需重起 | 掉线→快速登录 | 手动逐个 `unit.sh start`（`service.sh` 不自动起） |

「消息进不来」和「进程挂了」是两件事：桥接器只在收到 POST 时才做事，NapCat 掉线它不会报错。
所以 `bin/doctor.sh` 同时查单元状态**和** OneBot 的 `get_login_info`。

## 启动顺序

```
napcat → dsh（外部，只提示）→ bridge → web
```

后面的要连前面的端口，但**没有硬依赖**：桥接器起得比 NapCat 早只是暂时没有消息；
网关切得比桥接器早只是 `/bridge/` 先 502 几秒。所以顺序错了不会崩，只是短暂不可用。

`service.sh` **不执行这个顺序**：它只初始化目录/配置并退出，不自动起任何单元、不等
`sys.boot_completed`、不 chroot/mount。需要时按上面的顺序手动 `unit.sh start`。

## PID 语义（容易踩）

`unit.sh start` 起的是**看守子进程**，PID 文件写的是它；真正干活的 node 在
`$DATA/run/<单元>.pid.child`。但 **PID 文件不能全信**：重启、崩溃、手工 kill 都可能留下
过期 PID 或孤儿进程。`unit.sh stop` 现在做四步：

1. 读 PID 文件，校验命令行确实是本单元（`unit.sh` / `units/<name>/` / `run-<name>.sh`）；
2. 按命令行扫描 `/proc/*/cmdline`，找未登记的旧进程；跳过调用者 shell、`cd … && sh …`
   这类包装命令和当前 `unit.sh`；
3. 递归收集 `/proc/<pid>/task/<pid>/children` 的整棵子树（看守 → 子 shell → node → dsh）；
4. 先 TERM，最多等 5 秒，再 KILL；最后清 PID 文件。

所以 `unit.sh stop` 会一并收掉 node、正在跑的 dsh 孙进程和旧看守；
`unit.sh start` 发现未登记进程会拒绝启动并提示先 stop，避免两个实例抢同一个端口。

手工 `kill` 的如果是 `.pid.child`，看守会以为崩了并退避重启；要停服务请用
`unit.sh stop`，不要直接 kill。`service.sh` 开机拉起后，真正干活的 node 不是 PID 文件里那个，
排查端口占用要看 `ps -eo pid,ppid,args | grep <单元入口>`，或者直接 `unit.sh stop`。

## NapCat 的定位（不要过度管理）

NapCat 是**独立项目**：装一次、扫一次码，之后它自己跑。本模块只负责三条：

1. 拉起来（`unit.sh start napcat` → `bin/napcat-start-host.sh`）
2. 崩了退避重启
3. 停止时别杀错人（独立 PID 文件）

**不做**：不接管它的业务配置（OneBot 网络配置由 `bin/napcat-wire-onebot.sh` 一次性写入，
之后是它的）、不代它登录、不跟踪它的版本。

## 登录态与保活

- 票据在 `/opt/napcat/.config/QQ`，重启不会掉号
- 快速登录靠 launcher 注入 `-q <uin>`（uin 从 `onebot11_<uin>.json` 取）
- **禁止两个实例同时登同一号**：起之前先 `pgrep -af '^/opt/QQ/qq'` 确认是 0 或 1
- 桥接器重启不影响 QQ；只有 `napcat` 单元重启才涉及登录

## 容器路线的结论（已废弃）

原计划把 NapCat 放进独立 chroot 容器。实测这台机器的 proot 引擎里 `chroot` 一律
`failed to run command '/bin/bash': No such file or directory`，连静态 loader 和最小 rootfs 都不行，
所以改宿主直装。构建记录（rootfs 能拼出来但跑不起来）不再维护。
