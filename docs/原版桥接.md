# 原版 napcat-dsh-bridge（opt-in 单元 `legacy`）

> 目的：把从 `dsh-backup-20261025-1230` 复原的原始桥接作为**可选单元**接进模块，
> 保留原版的指令、会话、拟人化、小动作和管理/仪表盘。
> 边界：只跑宿主 node（`TYPE=exec`），不 chroot、不 mount；**默认不启动**，不影响开机。
> 依赖：`units/legacy/app/`、`$DATA/etc/legacy.json`、NapCat 的 3001 WS/HTTP、宿主的 `dsh`。
> 失败：缺 node/入口 → 78；配置/策略不合法由 app fail fast，supervisor 退避重启。

## 它和现在的 `bridge` 单元是什么关系

- `bridge`：当前 Magisk 版桥接（`units/bridge/bridge.mjs`），默认可用、长期维护。
- `legacy`：从原始 `napcat-dsh-bridge` 复原的完整桥接（`units/legacy/app/src/bridge.js`）。
  默认不启动；要用原版行为时手动起它，**同一时间只开一个**，否则同一条 QQ 消息会被回两遍。

## 第一次启动

```sh
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh start legacy'
```

首次会生成 `/data/adb/tinda-bot/etc/legacy.json`（0600）。如果已有
`$DATA/etc/bridge-policy.json`，会把其中的 `allowUsers`/`ownerUsers`/`allowGroups`
复制过来；没有就保留模板占位 `"0"`。**先确认白名单是自己的 QQ**，再重启单元：

```sh
su -c 'vi /data/adb/tinda-bot/etc/legacy.json'   # 或任何编辑器
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh restart legacy'
```

关键字段：

| 字段 | 含义 |
| --- | --- |
| `onebot.mode` | `forward-ws`（默认）/ `http` |
| `onebot.url` | WS 模式填 `ws://127.0.0.1:3001`；HTTP 模式填 `http://127.0.0.1:3001`（NapCat 动作地址） |
| `onebot.listenHost` / `listenPort` | 仅 HTTP 模式：本桥接接收事件的地址，默认 `127.0.0.1:3002` |
| `onebot.accessToken` | 留空；`run-legacy.sh` 会从 `secrets/napcat.token` 注入 |
| `dsh.command` / `dsh.profile` | 默认 `dsh` / `qq`，和模块一致 |
| `admin.port` / `panel.port` | 默认 6701 / 6702；与当前 `bridge` 的 6700 不冲突 |
| `policy.privateChat` / `groupChat` | 默认 `allowlist` / `mention`，空白名单不会放行 |
| `behavior.humanize` / `interactions` | 原版分气泡与 QQ 小动作 |

## NapCat 接线：WS 或 HTTP

原版默认走**正向 WebSocket**。重新跑一次接线脚本会把 3001 的
`httpServers[].enableWebsocket` 打开（HTTP API 仍然可用，当前 `bridge` 不受影响）：

```sh
su -c 'sh /data/adb/modules/tinda-bot/bin/napcat-wire-onebot.sh'
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh restart napcat'
```

如果 NapCat 已经用 HTTP 客户端把事件推到本机，也可以把 `legacy.json` 改成：

```json
"onebot": {
  "mode": "http",
  "url": "http://127.0.0.1:3001",
  "listenHost": "127.0.0.1",
  "listenPort": 3002
}
```

HTTP 模式下桥接在 `listenPort` 收 NapCat 的 POST 事件，再用 `url` 调
`send_private_msg` / `send_group_msg`。NapCat 的 HTTP 服务默认占用 3001，
所以桥接的 `listenPort` 默认是 3002。用接线脚本把事件推过去（只开 legacy 时）：

```sh
su -c 'BRIDGE_LISTEN=127.0.0.1:3002 sh /data/adb/modules/tinda-bot/bin/napcat-wire-onebot.sh'
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh restart napcat'
```

WS 模式不需要额外端口，推荐先用它。

然后 `unit.sh start legacy`。看日志：

```sh
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh logs legacy 80'
```

出现 `OneBot 已连接` 才是真的接上了；只有 `待机` 说明 WS 没通或 token 不对。

## 仪表盘 / 管理接口

- 仪表盘：`http://127.0.0.1:6702/`（当前只读仪表盘渲染：概览/会话/事件/配置）
- 管理接口：`http://127.0.0.1:6701/status`、`/inject`、`/command`
- token：`$DATA/state/legacy/admin.token`、`panel.token`（0600）

## 已知边界

- 原版 `panel-client.js`/`panel.css` 仍有缺口，当前用简化只读页；
- 原版 `commands.js` 的 `/help /status /new /sessions /ping` 已实测通过，
  `/ws`、`/model` 等后半段仍要继续回归；
- 假 OneBot WebSocket 已通过（`test/legacy-onebot.mjs`：私聊入站 → 假 dsh → `send_private_msg`）；
- 假 OneBot HTTP 已通过（`test/legacy-onebot-http.mjs`：POST 事件 → 假 dsh → POST `send_private_msg`）；
  真实 NapCat/QQ 联调还没做；
- 这是 `TYPE=exec`，**不会**碰 v0.2.37 的零开机动作、私有 namespace 和 chroot 安全层。
