# 单应用桥接（原版 napcat-dsh-bridge）

> 目的：把从 `dsh-backup-20261025-1230` 复原的原版桥接作为模块**唯一的**桥接进程，
> 保留原版的会话/工作区/模型/导出/管理面板，同时保留 v0.2.37 的零开机动作与挂载安全。
> 边界：只跑宿主 node（`TYPE=exec`），不 chroot、不 mount；默认不自动启动。
> 依赖：`app/`、`$DATA/etc/app.json`、NapCat 的 3001 WS/HTTP、宿主的 `dsh`。
> 失败：缺 node/入口 → 78；配置/策略不合法由 app fail fast，supervisor 退避重启。

## 形态

- 只有一个 `app/`（`app/src/index.js`），一个 `bridge` 单元，一份 `app.json`。
- `units/legacy` 和旧的 `units/bridge/bridge.mjs` 不再作为运行时；v0.2.43 只作回退。
- `units/napcat`、`units/web`、`units/dsh` 仍是外围服务；桥接只有一份。
- 原版能力（会话注册表、多工作区、`/ws`、`/ls`、`/model`、`/export`、DSH API/headless）
  保留；当前安全层（策略、补发、图片 SSRF、群上下文）并入同一个进程。

## 第一次启动

```sh
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh start bridge'
```

首次会生成 `/data/adb/tinda-bot/etc/app.json`（0600）。如果已有
`$DATA/etc/bridge-policy.json`，会把其中的 `allowUsers`/`ownerUsers`/`allowGroups`
复制过来；没有就保留模板占位。**先确认白名单是自己的 QQ**，再重启：

```sh
su -c 'vi /data/adb/tinda-bot/etc/app.json'
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh restart bridge'
```

关键字段：

| 字段 | 含义 |
| --- | --- |
| `onebot.mode` | `forward-ws`（默认）/ `http` |
| `onebot.url` | WS 模式填 `ws://127.0.0.1:3001`；HTTP 模式填 `http://127.0.0.1:3001`（NapCat 动作地址） |
| `onebot.listenHost` / `listenPort` | 仅 HTTP 模式：本桥接接收事件的地址，模板默认 `127.0.0.1:6700` |
| `onebot.accessToken` | 留空；`run-app.sh` 会从 `secrets/napcat.token` 注入 |
| `dsh.command` / `dsh.profile` | 默认 `dsh` / `qq`，和模块一致 |
| `dsh.models` | `/model` 的别名表；为空时只能看当前模型，不能切 |
| `admin.port` / `panel.port` | 默认 6701 / 6702 |
| `policy.privateChat` / `groupChat` | 默认 `allowlist` / `mention`，空白名单不会放行 |
| `behavior.humanize` / `interactions` | 分气泡、停顿、QQ 小动作 |
| `behavior.groupContext` | 群上下文：没 @ 的消息也记，被 @ 时注入最近几条 |

## NapCat 接线：WS 或 HTTP

默认走**正向 WebSocket**。接线脚本会把 3001 的
`httpServers[].enableWebsocket` 打开（HTTP API 仍然可用）：

```sh
su -c 'sh /data/adb/modules/tinda-bot/bin/napcat-wire-onebot.sh'
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh restart napcat'
```

HTTP 模式把 `app.json` 改成：

```json
"onebot": {
  "mode": "http",
  "url": "http://127.0.0.1:3001",
  "listenHost": "127.0.0.1",
  "listenPort": 6700
}
```

现有接线脚本默认就把 NapCat 事件推到 `127.0.0.1:6700`，不用改；如果改过
`BRIDGE_LISTEN`，让两边一致即可。

WS 模式不需要额外端口，推荐先用它。看日志：

```sh
su -c 'sh /data/adb/modules/tinda-bot/bin/unit.sh logs bridge 80'
```

出现 `OneBot 已连接` 才是真的接上了；只有 `待机` 说明 WS 没通或 token 不对。

## 常用指令

- `/help`、`/status`、`/new`、`/sessions`
- `/ws [路径|会话 id]`：切工作区或接回旧会话（admin）
- `/ls [子路径]`：只列当前工作区内（user；绝对路径和 `..` 会被拒绝）
- `/model [别名]`：查看/切换模型（admin，需要 `dsh.models`）
- `/context [clear]`：看/清本群上下文缓冲
- `/export`、`/compact`、`/goal` 等 DSH 原生命令透传

## 仪表盘 / 管理接口

- 仪表盘：`http://127.0.0.1:6702/`（概览/会话/事件/配置）
- 管理接口：`http://127.0.0.1:6701/status`、`/inject`、`/command`
- token：`$DATA/state/app/admin.token`、`panel.token`（0600）

## 已知边界

- 原版 `panel-client.js`/`panel.css` 仍有缺行，面板先用可用的只读渲染；
- `/model` 依赖 `dsh.models` 配置，未配置时只显示当前模型；
- 真实 NapCat/QQ 联调还没做；假 WS/HTTP 已通过：
  `app/test/legacy-onebot.mjs`、`legacy-onebot-http.mjs`、`commands.mjs`；
- 这是 `TYPE=exec`，**不会**碰 v0.2.37 的零开机动作、私有 namespace 和 chroot 安全层。
