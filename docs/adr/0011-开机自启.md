# ADR-0011：开机自启只拉 web，等待挪到后台脚本

> 状态：已采纳（v0.3.2）。取代 ADR-0008 里「开机零动作」的默认值，安全层本身不变。

## 背景

v0.2.36 因为 v0.2.35 在 `service.sh` 里等 `sys.boot_completed` 最多 180 秒、再 `sleep 20`、
然后一次拉起 4 个单元，导致部分设备开机被拖住，于是改成「service.sh 零动作，全手动」。

代价是：刷完模块重启后，8443 控制台不会自己起来，浏览器只看到 `ERR_CONNECTION_REFUSED`。
用户以为刷坏了，实际只是没人执行 `unit.sh start web`。每次重启都要记得手动起面板，
这和「装个模块就能用」的预期不符。

## 可选方案

1. **保持零动作 + 文档写清楚**：风险最低，但用户每次重启都要 adb/su 敲命令；不去看文档就等于坏了。
2. **把等待和启动搬回 service.sh**：等于回到 v0.2.35 的做法，事故根因（开机阶段阻塞）重现。
3. **service.sh fork 一个后台 boot-start.sh，等待与启动都在后台（选中）**：
   `service.sh` 仍然只做目录/配置初始化，然后立即 `exit 0`；等待开机完成、逐个 `unit.sh start`
   都发生在脱离的进程里，开机阶段不再有长 sleep。
4. **用 Android `init`/`late_start` 服务或 `post-fs-data` 常驻**：接管 Magisk 的生命周期，
   和 ADR-0001（不注入、不用 init 服务）冲突，还要处理 SELinux 域，收益不值。

## 决定

- 新增 `bin/boot-start.sh`：等 `sys.boot_completed` 最多 90 秒（45 × 2s），然后按
  `AUTO_START` 列表调用 `unit.sh start`；只认 `units/` 下真实存在、名字合法的单元。
- `service.sh` 只做初始化，然后 `( sh boot-start.sh & )` 后立刻退出，不 mount、不 chroot。
- 默认 `AUTO_START=web`：面板刷完就能开；`bridge`/`napcat` 仍手动起，
  避免白名单还没配好时开机自动回 QQ 消息。想全自动就写 `napcat bridge web`，
  想回到旧行为写 `off`。
- `bin/check-module.sh` 把这条契约固化：`service.sh` 必须调 `boot-start.sh`，
  且不许自己出现 `getprop sys.boot_completed` 或 `sleep 20`。

## 代价与残余风险

- 后台脚本仍是 root 身份、仍会在这台设备上起进程；开机阶段的失败只进
  `$DATA/logs/supervisor.log`，不会弹通知。
- 90 秒等不到 `sys.boot_completed` 就直接继续启动，等价于「早启动」，单元自己会重试/失败关闭。
- 默认只起面板，所以「重启后 QQ 机器人不回消息」仍是预期行为，需要手动起 `bridge`。

## 何时重审

- 出现新的开机卡顿投诉，且日志指向 `boot-start.sh`；
- 需要把 `bridge` 也做成默认自启（届时必须先确认白名单/策略默认拒绝仍然有效）；
- Android 侧提供可靠的「开机后延迟执行」接口，能替代自建轮询。
